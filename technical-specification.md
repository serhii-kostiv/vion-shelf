# Технічна Специфікація: Проєкт "VionShelf"

## 1. Огляд продукту (Product Overview)

VionShelf — це вебдодаток для каталогізації та трекінгу споживання мультимедійного контенту. Основна ідея полягає в тому, щоб дати користувачам змогу створювати кастомні "полиці" (колекції) для різних типів медіа (книги, фільми, аніме, ігри) з можливістю відстежувати прогрес, ставити оцінки та залишати нотатки.

### 1.1. Бізнес-цілі (MVP)

- Надати базовий інструмент для ручного створення колекцій та додавання елементів
- Закласти архітектурний фундамент для майбутньої інтеграції з зовнішніми API (TMDB, Google Books, IGDB, MAL)
- Забезпечити швидкий та безшовний UI завдяки SSR та оптимістичним оновленням

## 2. Технологічний стек та Архітектура

- **Frontend**: Nuxt 3 (SSR), Vue 3 (Composition API), Tailwind CSS
- **Бекенд**: NestJS (REST API)
- **База даних**: PostgreSQL
- **ORM**: Prisma
- **Аутентифікація**: JWT (Access + Refresh Token ротація), інтеграція через @sidebase/nuxt-auth (провайдер local)
- **Валідація**: Zod (спільні схеми для бекенду та фронтенду)

## 3. Схема Бази Даних (Database Design)

Архітектура БД побудована з урахуванням нормалізації для уникнення дублювання даних (паттерн Global Catalog + User Library).

### 3.1. User (Користувачі)

Відповідає за авторизацію та базовий профіль.

- `id`: UUID (PK)
- `email`: String (Unique)
- `username`: String (Unique, Index)
- `passwordHash`: String
- `hashedRefreshToken`: String (Nullable) — зберігаємо лише хеш для безпеки
- `createdAt` / `updatedAt`: DateTime

### 3.2. MediaItem (Глобальний каталог)

Єдине джерело правди про контент. Якщо 1000 користувачів додадуть гру "Відьмак 3", у цій таблиці буде лише 1 запис.

- `id`: UUID (PK)
- `type`: Enum (BOOK, MOVIE, ANIME, GAME, COURSE)
- `externalId`: String (Unique, Index) — ідентифікатор із зовнішнього API (наприклад, tmdb-123 або isbn-9780132350884). Для MVP, якщо юзер створює запис вручну, генеруємо кастомний унікальний рядок
- `title`: String
- `coverUrl`: String (Nullable)
- `metadata`: JSONB — гнучке поле для специфічних даних
  - Приклад для книги: `{"author": "Роберт Мартін", "pages": 464}`
  - Приклад для аніме: `{"studio": "Madhouse", "episodes": 24}`

### 3.3. Collection (Полиця)

Логічне групування контенту користувачем.

- `id`: UUID (PK)
- `userId`: UUID (FK -> User.id, Index)
- `title`: String
- `slug`: String (Unique, Index) — генерація з назви + random string для унікальних URL (напр., moia-manga-abc12)
- `description`: String (Nullable)
- `category`: Enum (відповідає MediaItem.type, або MIXED для змішаних полиць)
- `isPublic`: Boolean (Default: false)
- `createdAt` / `updatedAt`: DateTime

### 3.4. CollectionItem (Зв'язок Користувач-Контент)

Відображає прогрес конкретного користувача щодо конкретного медіа на конкретній полиці.

- `id`: UUID (PK)
- `collectionId`: UUID (FK -> Collection.id, Index)
- `mediaItemId`: UUID (FK -> MediaItem.id, Index)
- `status`: Enum (PLANNED, IN_PROGRESS, COMPLETED, DROPPED)
- `rating`: Int (Nullable, 1-10)
- `progress`: Int (Default: 0) — прочитані сторінки або переглянуті серії
- `notes`: Text (Nullable)
- `addedAt` / `updatedAt`: DateTime
- **Constraint (Обмеження)**: `@@unique([collectionId, mediaItemId])` — один і той самий фільм не може бути на одній полиці двічі

## 4. Специфікація API (REST Contracts)

Всі відповіді від API повинні мати єдиний формат (Response Envelope):

```json
{
  "data": { ... },
  "error": null,
  "meta": { "timestamp": "2026-02-25T19:15:25Z" }
}
```

### 4.1. Auth Module

- **POST /auth/register**
  - Body: `{ email, username, password, password_confirmation }`
  - Action: Створює юзера

- **POST /auth/login**
  - Body: `{ email, password }`
  - Action: Повертає accessToken (у тілі JSON) та встановлює refreshToken у httpOnly cookie

- **POST /auth/refresh**
  - Action: Читає cookie, валідує хеш у БД, видає нову пару токенів (Rotation)

### 4.2. Collection Module

- **GET /collections** — Отримати всі свої колекції (потребує авторизації)
- **POST /collections** — Створити нову полицю
- **GET /collections/:slug** — Отримати деталі колекції та всі її CollectionItem (join з MediaItem)

### 4.3. Media & Progress Module (Критична логіка)

- **POST /collections/:collectionId/items**
  - Body: Дані про медіа (назва, тип, externalId) + статус користувача (status, rating)
  - Логіка (Upsert): Бекенд спочатку шукає MediaItem за externalId. Якщо немає — створює. Далі створює запис у CollectionItem, прив'язуючи знайдений/створений mediaItemId до collectionId

- **PATCH /items/:id** — Оновити прогрес, статус або оцінку

## 5. Вимоги до Frontend (Nuxt 3)

### 5.1. Управління станом та Data Fetching

Необхідно створити кастомний composable `useApi` (wrapper над useFetch).

**Обов'язки useApi:**

- Автоматичне додавання baseURL
- Ін'єкція Authorization заголовка з поточним accessToken
- Перехоплення 401 помилки: Якщо запит падає з 401, useApi робить запит на /auth/refresh, оновлює токен і непомітно для користувача повторює оригінальний запит

### 5.2. Маршрутизація та Захист (Middleware)

**auth.global.ts**: Перевіряє стан сесії.

- **Публічні роути**: `/`, `/login`, `/register`
- **Захищені роути** (вимагають логіну): `/dashboard`, `/settings`
- **Гібридні роути**: `/c/:slug` (якщо колекція публічна — показуємо всім, якщо приватна — тільки власнику; перевірка відбувається на бекенді)

## 6. MVP (Мінімально Життєздатний Продукт)

Для першої робочої версії (щоб можна було викласти на сервер і користуватися) ми реалізуємо наступні сценарії (User Stories):

### Фаза 1: Фундамент (Auth)

- **US-1**: Як користувач, я можу зареєструватися, ввести свої дані і автоматично потрапити в систему без необхідності логінитися вдруге
- **US-2**: Як користувач, я залишаюся залогіненим навіть після перезавантаження сторінки або повернення на сайт через кілька днів (працює Refresh Token)

### Фаза 2: Створення простору

- **US-3**: Як користувач, я бачу порожній дашборд і можу створити нову колекцію, вказавши її назву (наприклад, "Прочитати у 2026") та категорію (Книги)
- **US-4**: Як користувач, я можу клікнути на колекцію і побачити її унікальну сторінку (поки що порожню)

### Фаза 3: Наповнення (Ручний режим)

> **Примітка для MVP**: ми не підключаємо зовнішні API для пошуку фільмів чи книг. Користувач вводить все ручками.

- **US-5**: Як користувач, перебуваючи всередині колекції, я натискаю "Додати елемент". З'являється модальне вікно, де я пишу "Чистий Код", вибираю статус "В процесі", вказую прогрес "50 сторінок" і зберігаю
- **US-6**: Як користувач, я бачу цей елемент у списку колекції. Я можу змінити його статус на "Завершено" і поставити оцінку 9/10, після чого дані миттєво оновлюються на бекенді

## 7. Масштабованість та Ризики (Edge Cases)

### Ризик: Забагато запитів при оновленні прогресу

Наприклад, юзер швидко клікає "плюсик" для збільшення серій аніме.

**Рішення**: На фронтенді впровадити debounce (затримку в 500мс) перед відправкою PATCH запиту на бекенд, або використовувати оптимістичні оновлення UI з фоновою синхронізацією.

### Ризик: Зміна структури даних при додаванні нового типу контенту

**Рішення**: Саме тому ми використовуємо колонку metadata типу JSONB. Вона дозволяє зберігати будь-які "кастомні" поля для різних типів медіа, залишаючи ядро бази даних незмінним.

### Ризик: Витік токенів

**Рішення**: Access Token живе 15 хвилин. Refresh Token передається виключно через httpOnly, Secure cookie, до якої JavaScript не має доступу.
